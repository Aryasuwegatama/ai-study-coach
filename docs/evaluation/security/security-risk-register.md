Related: [threat model](security-threat-model.md), [test catalogue](security-test-plan.md), [project risks in PRD Section 5](../../prd/05-build-workflow-evidence.md#risks).

This register tracks security/privacy exposure; Section 5 remains the project-level risk list. Likelihood and impact are qualitative planning estimates (Low/Medium/High), not measured probabilities or confirmed exploit findings. A control present in source is not a passed test. “Open” means review/verification or remediation is still required. No risk has been formally accepted. ## Tracking and response

At each stand-up, update the next action, owner, date and issue/PR link when one exists. Source observations above have **not** been filed externally by this task. Ask Arya to review auth, spaces and environment assumptions; ask Rashid to review upload/parser, job recovery, prompt and deletion observations. Review requests and approvals must be recorded when actually received, never inferred.

For suspected leakage, preserve only an anonymised reproduction, privately notify the credential/data owner and revoke affected credentials as needed; never paste the leaked value into an issue or a test report. For a failing ownership or integrity case, keep the test reproduction, identify the resource/service boundary and track the fix separately from this documentation task.

Risk acceptance requires an explicit decision by the responsible project owner, the reason, residual impact, expiry/revisit date and linked evidence. Until then, all rows remain open. The presence of a risk entry does not waive a P0 acceptance criterion.
