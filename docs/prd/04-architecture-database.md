# Capstone 2 PRD v1.2 — Section 4: Architecture & Database

Version 1.2 · 2 November 2026 · Owner: Arya

The app is one Next.js project (a modular monolith): screens, API routes and background workers live in one repository and deploy together to Vercel. Postgres (Neon) is the single source of truth for every record, including search vectors; private files live in Vercel Blob; QStash runs background steps; Gemini is called only from the server.

The **proposed** initial data model has 17 Core domain tables plus generated Better Auth tables. It is not migration-tested. Mastery is calculated from scored attempts on read rather than stored as a separate table.

This section turns Sections 1–3 into the structure the team builds.

## Request flow and folders

Authenticated student endpoints use thin routes, Zod validation and ownership-scoped feature services; trusted QStash/cron endpoints follow separate signature/secret verification. Shared adapters wrap the database, storage, AI and queue.

1. **Page or API route** (`src/app/…`) reads the request and validates it with the feature's Zod schema.
2. **Session check:** `requireUser()` returns the signed-in user or responds 401.
3. **Feature service** (`src/features/<feature>/server/`) runs the business rule and checks ownership through `requireSpace(spaceId, user)`, which responds 404 if the space is not theirs.
4. **Adapters** (`src/server/`) talk to Postgres (Drizzle), Blob, QStash and Gemini (`callAI()`). Features never call these services directly.
5. **Response** is JSON, with a stable error code and a safe message on failure.

│  │  ├─ (auth)/sign-in, sign-up

**Module rules:** a feature may import another feature only through its `server/index.ts`. Changes to `src/server/` or the database schema need a review from Arya or Rashid.

## Database tables (Core)

Seventeen proposed Core tables cover the user journeys. Domain IDs are UUID, times use `timestamptz` (except date-only revision due dates), names use `snake_case`, and scoped student content records normally carry `space_id`. Cleanup jobs intentionally can be **unscoped after deletion**; read paths still require authenticated ownership.

**Better Auth tables** (generated, not hand-written): `user`, `session`, `account`, `verification`. Three extra fields go on `user`:

- `role` — default `student`; sign-up cannot set it.
- `time_zone` — an IANA name such as `Australia/Brisbane`, saved from the browser at sign-in; used for "due today".
- `notifications_seen_at` — when the student last opened the bell.

Foreign keys to `user.id` must use the actual SQL type generated by the selected Better Auth adapter. Do not assume `text` or `uuid` without inspecting the generated auth migration.

| # | Table | Key columns | Rules it enforces |
| --- | --- | --- | --- |
| 1 | `study_spaces` | owner_id, name | One owner; name 1–150 characters |
| 2 | `materials` | space_id, original_name, blob_path, file_hash, page_count, char_count, status (`uploading, processing, review_topics, ready, failed`), stage, progress_done, progress_total, error_code, deleted_at | Unique (space_id, file_hash) while not deleted, so duplicate files are rejected; at most 20 per space (checked in code) |
| 3 | `chunks` | material_id, space_id, chunk_index, content, page_start, page_end, embedding `vector(768)`, embedding_model | Unique (material_id, chunk_index) |
| 4 | `topics` | space_id, name, normalized_name, description, status (`draft, confirmed, archived`), origin (`ai, manual`) | Unique (space_id, normalized_name) among confirmed topics, so there are no duplicate topics. Topic lists show confirmed topics only. |
| 5 | `material_topics` | **space_id**, material_id, topic_id, pages `int[]` | Composite FKs `(material_id,space_id)` → materials and `(topic_id,space_id)` → topics prevent cross-space material-topic associations. |

**Mastery is a query, not a table.** For one student and topic, it takes `attempt_items` from submitted attempts (skipping removed items and unanswered questions), keeps the latest answer per item, then the newest 10. Fewer than 5 means insufficient evidence; otherwise it computes the percentage, and below 60 means weak. It runs on every progress view.

**Database connection.** Plan for Drizzle with a verified Node.js PostgreSQL driver; use `pg` if transaction compatibility is confirmed. No Docker is required for local development. Production/preview Neon database separation is a configuration target, not a completed integration. Each developer has their own Neon branch (`dev-<name>`) with a dev database and a separate test database for integration tests. There is currently no GitHub Actions CI. Integration tests will use a separate local/test database once Neon is configured; verify present free-tier branch and compute limits instead of assuming a fixed ten-branch allowance. The first migration runs `CREATE EXTENSION IF NOT EXISTS vector`. Quiz submission and revision updates use short atomic database transactions. Job **claim** and **completion** transitions are transactional, but AI, Blob and QStash network calls happen **outside** SQL transactions; results are persisted idempotently.

**Indexes** (beyond primary and unique keys): `chunks (space_id, material_id)`; `learning_items (topic_id)`; `attempt_items (item_id)`; `revision_items (student_id, due_date)`; `jobs (user_id, finished_at)` for the bell; `jobs (user_id, kind, created_at)` for the daily limit. No vector index is required initially for small test data; measure retrieval p95 and introduce a scoped vector index only when query performance warrants it.

**Cross-space integrity is a database requirement.** Ownership checks and model citation-label validation are necessary but do not prevent all forged or buggy joins. Add composite unique reference keys (for example `(id, space_id)`) and composite foreign keys for `material_topics` and `item_sources`, so both ends of each relationship belong to the same Study Space. For `attempt_items`, include `space_id` and `set_id` on the child and enforce composite foreign keys to `attempts(id,space_id,set_id)` and `learning_items(id,space_id,set_id)`. Add matching parent UNIQUE constraints. This rejects responses to items from another quiz or workspace at the database layer. Test that mismatched associations are rejected.

**Deletion rules**

| Deleted | What happens |
| --- | --- |
| Account or space | Mark inaccessible, create a durable cleanup record containing restricted Blob object keys **before** deleting parent records. Delete dependent records according to approved retention rules; complete external Blob deletion with retriable cleanup independent of cascading rows. |
| Material | Mark unavailable to retrieval immediately; enqueue durable private Blob cleanup while the object key is still available. Delete chunks/vectors and affected source links consistently, retire unsourced learning items and their pending reviews, preserve or erase historical attempts according to an explicitly approved retention policy. Do not falsely claim Blob deletion before confirmation. |
| Topic with quiz history | Archived only |
| Item removed via report | Status becomes `removed`; it leaves new quizzes, revision and mastery |

## Background jobs

Every slow task is a row in `jobs`, moved forward one step at a time by QStash calling `POST /api/jobs/step`; the row, not the queue, is what the student sees.

| Job | Steps (each one call, well under 300 seconds) | Flow-control key |
| --- | --- | --- |
| `process_material` | verify → extract and chunk → embed (repeat per 50 chunks) → suggest topics | `processing`, parallelism 2 |
| `generate_quiz` | retrieve → write → check → top up (if needed) → publish | `generation`, delivery throttle 2; **database enforces max two full active generation jobs** |
| `generate_deck` | same as quiz | `generation`, QStash delivery throttle 2; shares the same two-job **database** admission pool as quizzes |
| `delete_files` | delete Blob files, retrying until done | none |

**How a step runs**

1. Verify the QStash signature. Unsigned calls get 401.
2. **Admit generation jobs atomically:** under a transaction-scoped PostgreSQL advisory lock, count `running` quiz/deck jobs and promote a queued generation job only if fewer than two exist. Keep the slot while that whole job progresses through multiple HTTP steps. Material processing is counted separately.
3. **Claim each step atomically:** match job ID and expected step; require no active unexpired claim (or expired lease recovery), assign a fresh random claim token, expiry and retry attempt. Duplicate delivery with a valid lease immediately returns 200 without doing work.
4. Do the external AI/Blob operation **outside the database transaction**. Upsert/commit idempotent outputs and advance the step in a short conditional transaction **only if the claim token and step still match**. Release the step claim when moving to the next queued step, retaining the overall job's generation slot.
5. Publish the next step after commit; a retryable dispatch record or scheduled reconciler must republish after a crash between commit and QStash publishing. On failure/lease expiry, replay only the incomplete step with a bounded attempt budget. Terminal success or failure releases the generation slot; the next queued job is then admitted. Cleanup jobs remain independent of deleted parents.

**Statuses the student sees** come from the material or set row: Processing (with "120 of 300 sections" while embedding), Review topics, Ready, Generating or Failed. The page polls every 3 seconds while anything is unfinished.

**Notification bell:** the last 20 of the student's jobs with `finished_at`, newest first. A dot shows when any of them finished after `user.notifications_seen_at`. No separate notifications table is needed.

**Daily limit:** count the student's `generate_quiz` and `generate_deck` jobs created since midnight in their time zone; refuse at 20.

**Local development:** use a verified QStash dev configuration/tunnel where needed; unit/integration tests call the step handler with a fake queue and an authenticated test signature. Do not assume a QStash local server exists without confirming the current tooling.

**Preview deployments.** Vercel preview protection may block QStash callbacks depending on project settings. Every published job step therefore carries Vercel's protection-bypass secret in the `x-vercel-protection-bypass` header, and `APP_URL` on previews must resolve to the correct verified preview host where callback delivery is supported. This is an integration test to perform, not a configuration that has already been validated.

**Daily clean-up.** A Vercel Cron job (once a day, allowed on the Hobby plan) calls `GET /api/cron/cleanup` with a secret. It:

- deletes materials stuck in `uploading` for over an hour, with their files;
- detects expired job leases and safely reclaims or fails the associated step after its retry budget, rather than unconditionally failing all jobs older than 15 minutes;
- re-queues any `delete_files` jobs that have not finished.

## Security rules

Ten rules, each with a test the security leads (Khushi, with Rashid reviewing) can write before the feature exists.

| # | Rule | Test |
| --- | --- | --- |
| 1 | Identity always comes from the session. Any `userId`, `ownerId` or `role` in a request body is ignored. | Send someone else's userId → ignored |
| 2 | Student APIs call `requireUser()` and owner-scoped `requireSpace()`; exceptions are explicitly isolated: Better Auth endpoints, QStash-signed workers and secret-verified cron endpoints. | Student B requests Student A's space/material/quiz/attempt/revision item → 404; unsigned worker/cron requests rejected |
| 3 | Vector search always filters by `space_id` in the same SQL query. | A chunk from another space never appears, even when it is the closest match |
| 4 | Correct answers, explanations and sources are never in the response for an in-progress attempt. | Inspect the attempt API response → no `correct_index` |
| 5 | Scores are calculated on the server from stored answers. | Submit a forged score → ignored |
| 6 | Files are in a private Blob store. Upload tokens are limited to one path, the 3 file types and 10 MB; downloads go through an owner-checked route. | Use another student's file path → denied |
| 7 | The job step route accepts only QStash-signed requests. | Unsigned or replayed call → 401 or no effect |
| 8 | Uploaded text is data, never instructions (Section 3 guardrails). | Prompt-injection test file |
| 9 | Passwords are hashed with Argon2id (custom Better Auth hasher); session cookies are httpOnly, secure and sameSite; Better Auth's built-in rate limiting is on for sign-in and sign-up. | Inspect the user table and cookies |
| 10 | Secrets live only in Vercel environment variables and `.env.local` (git-ignored); variable names are documented in this section, never values. Errors shown to users never include stack traces. | Manual staged-diff/secret review and local scanning before PR merge |

## Key decisions

- One modular Next.js App Router application with domain feature services; separate verification for authenticated APIs, signed QStash workers and secret-checked cron endpoints.
- The **17-table logical model is a proposal**, not verified SQL. Generate Better Auth tables first, then migrate in feature order while retaining the target schema contract.
- Strong database integrity uses same-Study-Space composite UNIQUE and FK relationships for materials, topics, sets, learning items and sources. `attempt_items` must be constrained to the **same set** as its parent attempt.
- `study_sets.material_ids` and `topic_ids` arrays are not relational FKs: validate that every generated item/topic/source belongs to the explicitly selected materials/topics before inserting published content, or normalise with join tables only when necessary. Never treat arrays as a database ownership guarantee.
- Mastery remains calculated from newest ten distinct eligible scored MCQs on read; no duplicate mastery table.
- QStash delivers short processing steps; PostgreSQL provides atomic generation admission for a maximum **two full active quiz/deck jobs**, conditional step claims, leases, idempotent writes and recovery when publishing the next step fails.
- Blob deletion uses independent persistent cleanup jobs with nullable parent references; queued cleanup cannot be cascade-deleted with the user, space or material whose file is being deleted.
- External API calls are **outside** database transactions. Scoring and revision changes occur atomically; authorisation and SQL constraints are backed by negative integration tests.
- UI/API/telemetry never expose signed provider secrets, correct answers before submission, another student's content, or raw prompts/lecture text.

## v1.2 migration and deployment gates

- Add explicit composite SQL constraints, not only Drizzle `relations()` metadata: `materials (id,space_id)`; `chunks (id,space_id)`; `topics (id,space_id)`; `learning_items (id,space_id)` are valid referenced unique pairs. Both sides of `material_topics` and `item_sources` carry the same `space_id`, and all insert paths must check owner and parent membership.
- Generation-slot accounting must be atomic and recoverable. A QStash per-request parallelism setting is not proof of a two-job cap across multi-request jobs.
- Deleting a Study Space, account or material must preserve the Blob cleanup intent outside the rows scheduled for cascade. Test an interrupted deletion and its successful retry.
- Before migration: generate the configured Better Auth schema; check `gemini-embedding-001` output dimension (768 if supported); verify Neon pgvector extension, database transactions and connection driver compatibility. The 17-table design is a proposal, not verified migrations.
- Vercel production is currently a boilerplate site; preview, collaborator-triggered builds, QStash callback authentication, provider quota and database isolation must all be validated before being described as working.

## v1.2 schema acceptance tests before first feature release

1. Generate Better Auth tables with the chosen adapter; inspect user ID type and confirm all domain FKs match.
2. Apply the incremental Drizzle migration on a clean dev database; verify pgvector is enabled before creating `vector(768)`.
3. Insert intentionally mismatched `material_topics`, `item_sources` and `attempt_items` rows: PostgreSQL must reject each even if a service validation bug exists.
4. Simulate two active generations and one additional request; the third must stay queued across multiple step requests, then start after a slot is released.
5. Simulate duplicate QStash delivery, expired lease, a process crash after database commit but before QStash publish, and an interrupted Blob deletion. Confirm eventual recovery and no duplicate published records.
6. Delete a material/space after persisting a cleanup intent; verify the opaque private Blob path remains available to the cleanup worker while all student routes stop returning the deleted content.
7. Run an unauthorised cross-account access test for every resource route, and a forged-score/double-submit test. Confirm completed attempts remain immutable after source retirement.
