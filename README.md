# AI Study Coach

AI-Powered Learning Analytics and Study Coach for Students.
Victoria University · NIT3003 Capstone 2 · Project 15.

Students upload study materials, confirm AI-suggested topics, generate cited quizzes and flashcards, track topic mastery, find weak topics and complete scheduled revision.

**Status:** in development. See the task map in [PRD Section 5](docs/prd/05-build-workflow-evidence.md).

Live: <https://ai-study-coach-zeta.vercel.app/>

## Documentation

- [`docs/prd/`](docs/prd/): the five PRD v1.2 sections, the source of truth for requirements
- [`docs/CONTRIBUTING.md`](docs/CONTRIBUTING.md): workflow, commands, folder structure and rules for working in this repository

## Stack

Next.js 16 (App Router), React, TypeScript, Tailwind CSS v4, shadcn/ui, pnpm, Better Auth (Google sign-in only; no passwords are stored), Neon Postgres with pgvector, Drizzle ORM, Vercel Private Blob, Upstash QStash, Vercel AI SDK with Google Gemini.
Planned: Vitest, Playwright, axe, k6.

## Getting started

```bash
pnpm install
pnpm dev
```

Open <http://localhost:3000>.

### Environment setup (new contributors)

The app needs a Neon Postgres database (with pgvector), a private Vercel
Blob store, an Upstash QStash account, a Google AI Studio (Gemini) API key
and a Google OAuth client. Sign-in is Google-only, so there is no password
to set up. Each developer uses their own development credentials, never
the project's Production ones (Security rule 10 in
[PRD Section 4](docs/prd/04-architecture-database.md)).

The app validates every environment variable on start-up. If any variable
is missing, every page and script fails, so complete all the steps below
before running the app.

**Credential sources:**

| Credential | Source |
| --- | --- |
| Neon connection strings for a personal dev branch (`DATABASE_URL`, `DATABASE_URL_UNPOOLED`, `DATABASE_URL_TEST`) | Provided by the project lead, who creates the branch |
| Dev Google sign-in client (`GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`), localhost only | Provided by the project lead |
| Gemini API key | Created by each developer in Google AI Studio |
| QStash token and signing keys | Created by each developer in a free Upstash account |
| Blob read/write token | Created by each developer in a private Blob store in their own Vercel account (never the project's store) |
| `BETTER_AUTH_SECRET` | Generated by each developer; never shared or reused |

#### 1. Values provided by the project lead

The project lead:

- creates a personal Neon branch (`dev-<name>`) with a `dev` database and a
  separate `test` database;
- adds the developer's Google account as a **test user** in Google Cloud
  (while the consent screen is in "Testing", only test users can sign in);
- sends the three Neon connection strings and the dev Google sign-in
  client's ID and secret **privately**. The dev client only works on
  `http://localhost:3000`, so it cannot be used against Production.

Secrets are shared only by private message or a one-time link that expires
after opening, such as Bitwarden Send or a 1Password share link. They are
never posted in group chats, GitHub issues or pull requests, or commits.

#### 2. Credentials each developer creates

- **Gemini:** create an API key in [Google AI Studio](https://aistudio.google.com/).
  Use the same model names as the rest of the team; the project lead can
  confirm them, and they are not secret. The embedding model must stay
  `gemini-embedding-001`, because the database stores 768-dimension
  vectors (PRD Section 3).
- **QStash:** sign up at [Upstash](https://console.upstash.com/), open
  QStash, and copy the token and the current and next signing keys (plus
  `QSTASH_URL` if the console lists one).
- **Blob:** in a personal [Vercel](https://vercel.com/) account, go to
  Storage, create a Blob store with **private** access, and copy its
  read/write token.
- **Better Auth secret:** run `npx auth secret`, or use any random string
  of 32 or more characters.

#### 3. Create `.env.local`

Create `.env.local` in the project root. Git ignores this file, so it is
never committed. Fill in every value:

```bash
# Neon: personal dev branch (provided by the project lead)
DATABASE_URL=           # dev database, pooled connection string
DATABASE_URL_UNPOOLED=  # dev database, direct connection string (migrations)
DATABASE_URL_TEST=      # test database on the same branch

# Private Blob (personal store)
BLOB_READ_WRITE_TOKEN=

# QStash (personal Upstash account)
QSTASH_TOKEN=
QSTASH_CURRENT_SIGNING_KEY=
QSTASH_NEXT_SIGNING_KEY=
# QSTASH_URL=           # only if the Upstash console shows one for the region

# AI (personal Gemini key; team model names)
AI_PROVIDER=gemini
GOOGLE_GENERATIVE_AI_API_KEY=
AI_MODEL_GENERATE=
AI_MODEL_CHECK=
AI_MODEL_EMBED=gemini-embedding-001

# Better Auth
BETTER_AUTH_SECRET=     # 32+ characters, unique to this developer
BETTER_AUTH_URL=http://localhost:3000

# Google sign-in: dev client (provided by the project lead)
GOOGLE_OAUTH_CLIENT_ID=
GOOGLE_OAUTH_CLIENT_SECRET=
```

`OAUTH_PROXY_SECRET` is not needed locally; only Vercel Production and
Preview use it. The full list of variable names is in
[PRD Section 4](docs/prd/04-architecture-database.md#environment-variables).

#### 4. Set up the databases

Run the migrations on both the dev and test databases. The test database
migration needs its **direct** connection string, which is
`DATABASE_URL_TEST` with `-pooler` removed from the host name.

```bash
pnpm run db:migrate   # dev database (reads .env.local)
```

Test database, in Git Bash:

```bash
DATABASE_URL_UNPOOLED="<test database direct address>" pnpm exec drizzle-kit migrate
```

Test database, in PowerShell:

```powershell
$env:DATABASE_URL_UNPOOLED = "<test database direct address>"; pnpm exec drizzle-kit migrate; Remove-Item Env:DATABASE_URL_UNPOOLED
```

Migrations are never run manually against the Neon `main` branch, which is
Production. Vercel migrates it automatically on deploy.

#### 5. Verify the setup

```bash
pnpm run check:connections   # database, Blob, QStash, Gemini
pnpm run check:auth          # sessions, sign-out, Google sign-in URL, rate limiting
pnpm run check:spaces        # Study Space create, rename, delete and ownership
```

Each check prints only pass/fail lines and short, safe messages, never a
secret or session token. The checks create and delete their own test users
and never touch real accounts.

Google sign-in cannot be scripted, so test it manually: run `pnpm dev`,
open <http://localhost:3000/sign-in> and select "Continue with Google". If
Google reports that access is blocked, the account has not yet been added
as a test user.

If a secret is ever exposed publicly or committed by mistake, report it to
the project lead immediately so it can be rotated.
